## 关键源码发现及症状解释

### 1. 不完整的TinyUSB退栈是最有源码依据的候选之一

1.5.0的[卸载函数tinyusb.c:69](https://github.com/espressif/esp-usb/blob/20389182dbfd49f600f9fe56b70485f244b48087/device/esp_tinyusb/tinyusb.c#L69)
只调用tinyusb_free_descriptors并usb_del_phy；没有tusb_stop_task、tud_disconnect或完整TinyUSB/DCD去初始化。
[tusb_tasks.c:27](https://github.com/espressif/esp-usb/blob/20389182dbfd49f600f9fe56b70485f244b48087/device/esp_tinyusb/tusb_tasks.c#L27)
的任务仍循环tud_task；其:71提供stop函数，但上述切换路径不调用。

【推断】释放OTG PHY/CDC对象后，任务/设备栈仍可存活，存在跨核事件/中断与切换交错的可靠性风险。
源码也没有明确的主机断开观察间隔、重枚举确认或失败后恢复原CDC的流程。
更细的证据：usb_del_phy的注释提到disable pads，但S3的实际HAL→LL调用只清pad_pull_override，
随后关USB_WRAP时钟；不能单凭注释认定主机已经观察到一次有效断开。
具体D+/D-断开持续时间、控制器切换的电气效果仍未测量。
这可能造成“旧控制口已失效、新控制器尚未被确认”的半切换，而非完整退出USB栈。
**不能把这一缺口直接断言为该实机必然失败的唯一原因。**

限定：descriptors_control.c:288的free仅在TUD_OPT_HIGH_SPEED下释放other_speed；S3不是HS目标，
不能谎称这里已经证明S3的默认描述符发生heap use-after-free。确认的是未停止任务/完整退栈缺口。

### 2. PHY错误可在控制口已拆除后被静默吞掉

[IDF usb_phy.c:272](https://github.com/espressif/esp-idf/blob/9d7f2d69f50d1288526d4f1027108e314e8c879f/components/usb/usb_phy.c#L272)
校验target/controller，申请资源，在内部PHY仍IN_USE时返回ESP_ERR_INVALID_STATE（:285-296）。
usb_del_phy（:368）释放上下文、内部PHY记录并关闭不再使用的USB_WRAP时钟。

【离线验证】对原始initJtag/end函数注入卸载失败→PHY仍占用，或新PHY申请失败，
函数仍结束而不报告失败，CDC已被拆除且没有回退。因此“不能打开旧COM”不等于“1001已切换成功”。
实际usb_new_phy返回值、是否重启/挂起和主机枚举时间均未采集，不能确认实机走了哪个错误分支。

排除一个无依据假设：清零target不是无效target。
[hal/usb_phy_types.h:24](https://github.com/espressif/esp-idf/blob/9d7f2d69f50d1288526d4f1027108e314e8c879f/components/hal/include/hal/usb_phy_types.h#L24)
定义USB_PHY_TARGET_INT=0；mode=DEFAULT、speed=UNDEFINED也为0。
Serial/JTAG分支设置内部控制器模式，HAL重新映射内部PHY并启用pad。
没有依据说“少设置target/otg_mode所以一定失败”。

jtagPhy局部句柄不会因为离开函数而自动释放，但丢失了后续管理入口。
TinyUSB静态phy_hdl在卸载后未置空；若没有重启/重新安装就重复退栈，可能再次传入已释放句柄。
这也是不要盲目反复PROGRAM的重要原因，不能通过多试几次来证明安全性。

### 3. Windows串口发现有盲区（后续已确认当前4002为Present）

[port_tool.py:105](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/scripts/port_tool.py#L105)
只在pyserial.comports里找1001；它不能证明没有COM绑定的USB/JTAG PnP接口不存在。
控制口使用Win32_SerialPort、303A:4002、SOLREADER串号过滤并按MI排序（:15-51、:121），COM6不是恒定身份。
programming分支发送PROGRAM后只等3秒（:233-250），既无ACK，也无USB父设备/非串口接口枚举检查。
【离线验证】假端口/时钟实验复现：无COM的设备无法被该列表发现；4秒后出现的端口被3秒窗口漏掉。
这只证明发现逻辑的局限，不证明这台电脑已经有1001或延迟恰为4秒。

esp_tinyusb默认VID为Espressif，usb_descriptors.c:18按0x4000|CDC数量等构造PID，双CDC可解释应用4002；
这与固定硬件USJ的1001不同，不能因能访问4002就宣称下载控制器已启用。
在取得PnP反馈前，显示4002不能区分历史节点与当前接口；后续反馈已确认当前MI_00/MI_02为Present且健康。
Win32 WinError31是一般设备失败；不能把它直接等同设备管理器ProblemCode31或断言必须换驱动。
若真正的1001 USB父节点没有出现，单纯改串口/JTAG驱动不能证明可修复设备端PHY切换。

### 4. 其他候选和现阶段不支持的推断

真实eFuse、USB Serial/JTAG模块禁用、生产配置差异、枚举/电源状态与软件重启均待验证。
IDF USJ_ENABLE_USB_SERIAL_JTAG默认y，HAL会映射内部PHY、启用pad；源码没有证明必须补一个串口driver_install才可枚举。
官方USB接入GPIO检测会持有light-sleep锁，不能忽略这点而直接断言“就是自动休眠”。
版本字符串不是实机完整SHA，公开默认配置不是实机eFuse。

**优先判断：设备端退栈/PHY/主机重枚举未完成或未被正确观测；不能直接归因驱动/硬件。**

## 恢复与备份的先决条件

1. 获得授权后先证实稳定USJ/ROM或可用JTAG协议通路，记录明确入口及**不依赖当前应用还能重新进入**的方式。
2. 核对实际芯片/修订、Flash容量、分区、当前启动槽与otadata，而不是假定64MB或app0在运行。
3. 核对安全策略的可观察状态：读保护、加密、Secure Boot、download/JTAG禁用；不打印/上传密钥，不烧位。
4. 在允许的模式下两次独立全量读回、大小与哈希一致；另保存引导、分区、otadata、双应用及NVS/校准/配对/书籍，全部私密存放。
5. 区分密文/明文、地址绑定和签名；“读到了dump”不等于可按原地址安全写回，也不等于能写未签名自定义固件。
6. 先有可核验原厂镜像和匹配的恢复步骤，优先在备用硬件验证恢复；没有备用硬件时不能靠唯一设备故意变砖来证明E。
7. 不运行整包flash.sh、桌面verify、unpair-remote、FactoryReset或随意改分区来获得所谓备份。

回滚：[BootLoopDetection.cpp:26](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Misc/BootLoopDetection.cpp#L26)
对esp_partition_read取逻辑反：ESP_OK=0时立即false，成功读取反被拒绝。
【离线验证】原函数在假分区/返回值下复现：成功+正确头拒绝，错误+由桩填入magic头反而通过。
后者是控制实验，不声称真实错误必定会填入该头。
3/9/12/15次panic/WDT先清当前阅读/删文件/软/硬清除，18次才尝试Rollback；
不存在独立factory app槽。**严禁通过反复崩溃或复位尝试触发“救援”。**详见docs/07。

## 历史最小实验：只读PnP观察（用户已完成，不再推荐重复）

这是**待另行授权的实验设计，不是本轮要求用户立即操作眼镜**。不重复旧PROGRAM测试。
目的：先判断4002是Present还是历史节点，1001是否存在于非COM接口；不验证写入。

步骤（约1分钟；若眼镜已在正常状态连接，不重新插拔、不折叠/复位）：
1. 确认仍可正常阅读；不启动刷机/调试/串口软件，保持既有连接和电源状态。若已有设备任务在运行，不强制终止或关闭可能改变DTR/RTS的端口，只记录当前情况。
2. 在Windows PowerShell仅查询所有匹配USB节点（不运行port_tool，不打开COM）：

```powershell
Get-PnpDevice | Where-Object { $_.InstanceId -match '^USB\\VID_303A&PID_(4002|1001)' } |
ForEach-Object {
    $d = $_
    [pscustomobject]@{
        Status = $d.Status
        Class = $d.Class
        Name = $d.FriendlyName
        Present = (Get-PnpDeviceProperty -InstanceId $d.InstanceId -KeyName 'DEVPKEY_Device_IsPresent' -ErrorAction SilentlyContinue).Data
        Problem = (Get-PnpDeviceProperty -InstanceId $d.InstanceId -KeyName 'DEVPKEY_Device_ProblemCode' -ErrorAction SilentlyContinue).Data
        Service = (Get-PnpDeviceProperty -InstanceId $d.InstanceId -KeyName 'DEVPKEY_Device_Service' -ErrorAction SilentlyContinue).Data
        HardwareIds = (Get-PnpDeviceProperty -InstanceId $d.InstanceId -KeyName 'DEVPKEY_Device_HardwareIds' -ErrorAction SilentlyContinue).Data
    }
} | Format-List
```

只报告VID/PID、MI、Present、状态/Problem和Service；完整InstanceId、序列号、旧日志留本地，不公开提交。
3. 若保留当次失败日志，核对发送/失去COM/设备到达的时间与节点类型，缺资料就标未知；不为补日志再次PROGRAM。

预期分支：
- Present1001父设备/接口存在但无COM：先核对已有绑定/Problem；发现脚本假阴性成为可验证候选，**不马上改驱动或运行OpenOCD**。
- 只有非Present4002：旧设备名称不足以证明当前状态；B仍未证实。
- Present4002且健康、无1001：现在处于正常运行枚举，不能从当前快照反推过去程序有没有执行。
- Present4002不健康或设备描述符失败、无1001：支持半切换/枚举失败候选，但仍不是精确根因。

停止条件：状态/阅读发生异常、目标存在多个无法区分的303A设备、系统要求装/换驱动、工具试图打开串口/复位/写入，立即停止；不追加reset/flash/erase。
此观察不改变设备，正常情况下无需恢复措施。若设备本来已异常，只记录后停止；
仅采用此前已经验证过的用户恢复方式或厂商明确的恢复步骤，不能把重插/未知按键组合承诺为可靠恢复。

**当时推荐的路径（后续反馈见docs/14，已停止重复观察）**：现有USB连接上的USJ→ROM/esptool（不拆机），先用上面的独立PnP观察解决发现盲区。
若无1001且没有厂商明确可返回正常阅读的编程/退出步骤，则**目前没有足够条件安排下一轮主动切换实验**。
下一阶段必须先取得可靠退出/恢复依据，再单独批准一次带枚举时间线和停止条件的模式切换；
没有新证据不再次盲发PROGRAM。即使1001出现，也只改善B的枚举部分，C/D/E仍另行验证。
