## USB 与 PROGRAM

【源码确认】[src/Communications/USBSerial.cpp:111](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Communications/USBSerial.cpp#L111) begin 安装 TinyUSB，
CDC ACM_0 为控制/传输，ACM_1 为日志；rxCommandCallback 向注册 listener 分发数据。
[src/Misc/DirectCommand.cpp:50](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Misc/DirectCommand.cpp#L50) PROGRAM 调用 disableLogging → initJtag，
不发送明确 ACK，也不直接写 Flash。
[src/Communications/USBSerial.cpp:16](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Communications/USBSerial.cpp#L16) initJtag 先 end（反初始化双 CDC 和 TinyUSB），
再 usb_new_phy(controller=USB_PHY_CTRL_SERIAL_JTAG)，未检查其返回值。
这描述的是运行时 USB PHY 切换，不是已证明进入 ROM 下载模式。

【源码确认】[scripts/port_tool.py:105](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/scripts/port_tool.py#L105) Windows JTAG 查找 VID:PID=303A:1001；
正常控制口按303A:4002、通用 USB serial 字符串和 MI 顺序筛选，非固定 COM。
find_port programming（233行）若未发现 JTAG，打开正常控制口并发送 PROGRAM，
等待3秒后查找新接口；find_port logging 发 LOGGING_ON，
reset_jtag 改 DTR/RTS。
【推断】Windows Win32_SerialPort、接口驱动、枚举时间和未经检查的 PHY 返回值均可能影响发现；
不能据源码确定用户 WinError31/JTAG 失败原因，不能贸然换驱动或再次强制复位。

【源码确认】Makefile 的 flash 依赖 build，并调用具有上述副作用的端口发现；
CI 生成 flash.sh 写 bootloader、partition table、initial OTA data 和 app0。
官方 README/Makefile 中还有 erase/unpair/eFuse/OpenOCD 建议，均已审计而未执行，
不能优先于本项目设备安全规则。

## 官方 OTA

【源码确认】[src/Communications/FirmwareDownload.cpp:19](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Communications/FirmwareDownload.cpp#L19) FirmwareDownloader
通过 SindarinAPI 查询版本，Wi-Fi 优先、条件 BLE proxy 回退，
读取云 Token、比较版本、按服务端 URL 流式下载：
Update.begin(contentLength,U_FLASH) → setMD5 → write → end（或失败 abort）。
【源码确认】固定 astubs 8347f0aa4e1113e5b2f034d072550353885e6d2f 的
[src/Update/Updater.cpp](https://github.com/sindarin-inc/astubs/blob/8347f0aa4e1113e5b2f034d072550353885e6d2f/src/Update/Updater.cpp)
begin 选择 esp_ota_get_next_update_partition，受分区大小限制；
end 验证 MD5 并设置启动分区。FirmwareUpdateScreen 组织下载/安装 UI 与重启。
skipInstall 不代表无写入：下载过程中已写另一分区。
【推断】MD5 验证下载一致性，不是密码学签名或可信来源认证的充分证明。
【待实机验证】服务在线性、断网/取消/断电语义、更新失败回退、旧版本兼容、可用空闲槽。

## 分区与发布包

【源码确认】[esp32s3-64MB.csv](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/esp32s3-64MB.csv) 声明双 OTA 应用槽，无独立 factory app。
【离线验证】官方 Release ZIP 的 partition-table.bin 解出：
| 名称 | 起始地址 | 长度 |
| --- | --- | --- |
| nvs | 0x9000 | 0x5000 |
| otadata | 0xe000 | 0x2000 |
| app0 | 0x10000 | 0x400000 |
| app1 | 0x410000 | 0x400000 |
| coredump | 0x810000 | 0x10000 |
| data | 0x820000 | 0x37e0000 |

与源 CSV 一致；data 名义 subtype=spiffs，文件系统使用另一个抽象/组件，
不能由分区名字认定实机数据格式。
官方 ZIP 39,030,174字节；SHA-256 已核验，bootloader/app/partition 等分文件哈希
见 release_v1.6.0.json。应用版本字符串匹配，但没有读取用户设备。
发布包 flash.sh 覆盖引导/分区/otadata 的行为不是“只更新应用”，绝不能直接运行。
源 sdkconfig Flash mode=qio，包脚本参数=dio，有待核验。
64MB 是源码/包配置，不是 FREE_SPACE 推出的真实容量。

## 回滚审计的明确风险

【源码确认】[src/Misc/BootLoopDetection.cpp:25](https://github.com/sindarin-inc/embedded-app/blob/7dcf0850daa5cec076c8d68e2f56cf413ff707aa/src/Misc/BootLoopDetection.cpp#L25) PartitionIsBootable 中
esp_partition_read 返回值被逻辑取反后作为提前返回 false 的条件。
ESP_OK=0 时 !0 为 true，因此成功读取也提前拒绝分区。
【推断】正常可读分区可能无法通过此回滚判定，错误读取还可能使用未初始化 buffer；
必须用假分区和可控返回值离线验证并制定修复，不能认定可自动恢复。

【源码确认】BootLoopCheck 仅特定 panic/WDT 增加 RTC badBootCount，
3次清当前书籍、9次删除文件、12次软恢复出厂、15次硬恢复出厂、18次才调用 Rollback。
GoodBootTimer 在60秒后清计数；断电/其他重启可能改变计数持续性。
【推断】在尝试回滚前已经可能损失书籍、设置、配对/用户数据，
不是可接受的“保留数据升级恢复”保证。
本轮只记录风险，没有改写官方仓库，也未运行任何 reset/erase。

## 安全与恢复尚缺的证据

【源码确认】已检查的 sdkconfig.defaults* 没有显式启用 Flash Encryption、
Secure Boot 或 IDF bootloader rollback 的条目；
发布分区 flags 为0，app secure_version=0。
【待实机验证】这些都不能证明设备 eFuse 没启用安全功能；
须另核实实际安全配置、读回可用性、镜像签名/加密和恢复限制，
禁止为查询而执行 eFuse burn 或任何不可逆修改。

【阻断】仍无可靠的用户原厂全量备份、重复读回校验、
实机分区/容量、NVS/校准/配对数据私有备份、可用编程通路、
恢复驱动、板级恢复设计和真实恢复记录。
先完成离线恢复逻辑审查，再规划获授权的只读备份阶段。
唯一设备可正常阅读是必须保持的基线。
